# Feature

You own the design; the tests come from it, the code makes them pass. This is the light track: no research, spec or plan file, the design said in chat. A feature the user wants researched, brainstormed and specced first takes the full track, `/alpha:brainstorm <task>`.

1. Research the code. Run Investigation steps 1 to 4 over the part of the project the feature touches: how it works today, what the change must reach (callers, tests, fixtures, config, docs), and what it could break for users (`scope-first`).
2. Find the product areas the feature needs that are still open (project.json's `areas`): a UI needs ui and accessibility, stored data needs data, a deployed component needs observability, calls between components need architecture, errors users see need errors, a budget needs performance, a visual needs the design language, sign-in or permissions need auth. Name each to the user with its `/alpha:update <area>` request; don't settle it here.
3. Name the data shape before any logic: the types, the states and what moves between them, and the structure that holds them (a typed model, a table, a state machine) rather than scattered conditionals. Keep the structure the codebase already has unless it can't hold the feature.
4. State the design in chat, in a few lines: the approach and why the others don't fit, the data shape, where the code goes, what changes for callers, the failure paths. Mark your calls as yours and go on (SKILL.md section 3, First message). Ask only what changes what gets built and only the user can answer, one question at a time; a question you could settle by running something goes to the Prototype playbook. When `docs/alpha/specification.md` lists requirements, name the one the feature serves; one it doesn't list yet is the user's to add with `/alpha:update requirements`, so say so.
5. Write the tests at the levels the project's testing answers give (CONTRIBUTING.md, Testing), each asserting what a user of the code can observe and naming the product requirement it covers (`R<n>`) when there is one. Run them and paste the output: each must fail on the missing behavior, not on a typo or an import.
6. Write the smallest code that makes them pass, keeping the project's principles; delete what the change makes dead first (`subtract-first`).
7. Update the docs that move with the changed paths (CONTRIBUTING.md, Documentation) (`docs-with-code`).
8. Verify. The tests pass, and each behavior is exercised on the real thing where you can (run the CLI, the app, the endpoint), with what happened pasted. A behavior you couldn't exercise is reported as unverified, not passed. When the feature created the component's entry point, put its command in CLAUDE.md's `run` row.
9. Finish with Done (SKILL.md section 3): the tests, the code and the docs committed together, one logical change per commit (`clean-history`).

**Reply:** the design as built, each behavior with its test and result, the choices you made, the open product areas with their `/alpha:update <area>` requests, and what is left open.
